# Traps I fell for

These are the topics I got wrong in practice questions, grouped by the four exam domains, with the one rule that fixed each. Four of them caught me more than once: partitioning vs clustering, forecasting with the wrong model type, dashboard data credentials, and the two roles needed to run a query.

## Domain 1: Data preparation and ingestion

| What I picked or thought | What is right | The rule I use now |
|---|---|---|
| A data lake is for real-time analytics and a warehouse is for long-term storage. | A lake stores raw, unprocessed data. A warehouse stores processed, organized data. | Ask what is stored, not when it is queried. Raw is the lake, processed is the warehouse. |
| "Load into a staging area, then transform" sounded like ELT to me. | That is ETL when the staging area sits before the warehouse. In ELT the transform runs inside the warehouse. Staging tables inside BigQuery are still ELT. | Where does the compute happen? Inside the warehouse is ELT. Somewhere else first is ETL. |
| Dataflow for a visual, drag-and-drop pipeline. | Dataflow is code (Apache Beam) or templates you fill in. The two visual tools are Dataprep and Cloud Data Fusion. | Visual and cleaning one file is Dataprep. Visual and connecting many systems is Data Fusion. |
| Cloud Data Fusion to bring Google Ads, YouTube, or Amazon S3 data into BigQuery on a schedule. | BigQuery Data Transfer Service. It is the managed, scheduled loader for those sources. | SaaS or S3 into BigQuery on a schedule is BigQuery Data Transfer Service. |
| I mixed up the three services with "transfer" or "migration" in the name. | Storage Transfer Service moves files into Cloud Storage, not into BigQuery. BigQuery Data Transfer Service loads into BigQuery. Database Migration Service moves a live database into a managed database such as Cloud SQL. | Name the destination first: a bucket, BigQuery, or a database. |
| Moving an app's database into BigQuery. | BigQuery is for analysis. It is not the backend of a website. An app database migrates to Cloud SQL with Database Migration Service. | Apps write to Cloud SQL. People ask questions in BigQuery. |
| Replacing bad values with 0 so the type conversion would not fail. | `SAFE_CAST` converts the value or returns NULL, with no error. A 0 is counted in averages and skews them. A NULL is skipped. | A bad value becomes NULL through `SAFE_CAST`, never a made-up 0. |
| A scanned PDF counted as semi-structured data. | Semi-structured means tags or keys with a flexible or nested shape, such as JSON and XML. A scanned PDF is unstructured. | Keys or tags mean semi-structured. Scans, images, and audio are unstructured. |
| Newline-delimited JSON with schema auto-detection as the best format for a batch load. | Avro. The file carries its own schema and is the fastest format to load. | Fast and reliable batch load into BigQuery: Avro. |
| With nested JSON, I did not know a RECORD from a REPEATED field. | A RECORD is a nested object (a STRUCT). A REPEATED field is an array. `UNNEST` turns the array into rows so you can filter and join on it. | An object is a RECORD, a list is REPEATED, and `UNNEST` opens the list. |
| Dataflow to run data quality checks without writing code. | A data quality scan in Knowledge Catalog (used to be Dataplex). You define rules, not a pipeline. | Quality checks with no code: a Knowledge Catalog scan. Dataflow is for moving and changing data. |
| In a Datastream message, I thought the "change log" was the part that holds the changed values. | The changed values are in the payload. The other parts are metadata. The change log is what Datastream reads on the source side. | Metadata is context, payload is the values, the log is the source. |
| AlloyDB for a global relational database with 99.999% availability. | Spanner. | Global, relational, and five nines: Spanner. |
| Bigtable for app documents that sync to devices in real time. | Firestore. Bigtable is for massive time-series writes and lookups by row key. | Documents with live sync to apps: Firestore. A flood of timestamped rows: Bigtable. |

## Domain 2: Data analysis and presentation

| What I picked or thought | What is right | The rule I use now |
|---|---|---|
| A standard view for a result that must be both fresh and fast. | A materialized view. It stores the result and BigQuery keeps it refreshed. A standard view re-runs its query every time. | Fresh and fast: materialized view. |
| Adding `LIMIT` makes a query cheaper. I also mixed up partitioning and clustering. | `LIMIT` trims the rows you get back, but the scan is still billed. Cost drops when you filter on the partition column and select only the columns you need. Clustering keeps rows sorted by up to four columns so filters can skip blocks. | Cut cost with a partition filter and fewer columns. `LIMIT` is not a cost tool. |
| `LINEAR_REG` to forecast a value over time. | `ARIMA_PLUS`. It learns from the past values of the same column over time. With `ML.FORECAST` you only give a horizon. With `ML.PREDICT` you bring the rows to score. | Future values over time: `ARIMA_PLUS`. Predict means I bring rows, forecast means I bring a horizon. |
| Training a model to generate text when I had no labeled examples. | Use a pretrained Gemini model through a BigQuery remote model and `ML.GENERATE_TEXT`. Training needs labels. | No labels and the task is text generation: a pretrained model called from SQL. |
| BigQuery ML on the image metadata to classify images with my own labels. | AutoML image classification. The answer is in the pixels, and metadata says nothing about pixels. | Answer in the pixels: an image model. Answer in the columns: BigQuery ML. |
| I expected k-means to hand me named groups. | K-means is unsupervised. You choose only how many clusters. It returns a cluster number per row, and naming the groups is your job. | Known categories with labels: classify. No labels: cluster, then name the groups yourself. |
| Dimensionality reduction to sort unlabeled items into groups. | Clustering. It sorts rows into groups. Dimensionality reduction shrinks the number of columns. Both are unsupervised, which is why they are easy to mix up. | Sorting rows into piles is clustering. Shrinking columns is dimensionality reduction. |
| I swapped precision and recall. | "Catch them all" is recall: you are afraid of missing one (a false negative). "Only flag the real ones" is precision: you are afraid of a false alarm (a false positive). | Read which mistake costs more in the scenario. Lowering the threshold buys recall and spends precision. |
| Explainable AI as the tool that automates and orchestrates an ML workflow. | Pipelines in Agent Platform (used to be Vertex AI). Explainable AI tells you why a prediction happened. It orchestrates nothing. | "Automate", "orchestrate", and "serverless" for ML point to Pipelines. |
| I mixed up Model Registry and Artifact Registry. | Model Registry holds model versions and is where you deploy from. Artifact Registry holds containers and packages. | Models go in Model Registry. Containers and packages go in Artifact Registry. |
| A BigQuery view to give everyone one governed definition of a metric. | Looker with LookML. The metric is defined once in the model and every dashboard reuses it. | One trusted definition of a metric: Looker and LookML. |
| I mixed up LookML dimensions and measures. | A dimension is a field you group by. A measure is an aggregate, for example `type: sum`. A view describes a table and an explore is what users query. A filter on a measure behaves like `HAVING`. | Group by it: dimension. Aggregate it: measure. |
| I mixed up a Looker custom field and a table calculation. | A custom field becomes part of the SQL query. A table calculation runs on the results after the query comes back. | In the query: custom field. On the returned rows: table calculation. |
| In Data Studio (used to be Looker Studio), I thought viewers needed their own access to the BigQuery table, and that sharing the report was the same thing as sharing the data. | Two separate settings. Share decides who can open the report. Data credentials decide whose login runs the query. With owner's credentials, viewers see the charts with no access to the table. With viewer's credentials, each viewer needs their own access. | Share is who opens. Credentials are whose login queries. |
| I mixed up `LAG` and `LEAD`. | `LAG` reads the previous row. `LEAD` reads the next row. | `LAG` looks back, `LEAD` looks ahead. |
| Dataflow for pandas-style Python on very large BigQuery tables. | BigQuery DataFrames (the `bigframes` library). You write pandas-style code and the work stays in BigQuery. | pandas feel on BigQuery-size data: `bigframes`. |
| A missing comma between two column names in SELECT would raise an error. | It runs. The second name becomes an alias for the first, so you get one column under the wrong label. | No comma means alias. It fails silently, so count the columns. |
| When a "per category" count looked wrong, I blamed the GROUP BY column. | Grouping by the "per" column was right. The problem was `COUNT`, which counts rows, not distinct values. | "Per X" means GROUP BY X. Unique things need `COUNT(DISTINCT ...)`. |
| Exporting data so spreadsheet users could work with BigQuery tables. | Connected Sheets. It is the Sheets interface on live BigQuery data, with no export. | Spreadsheet users on BigQuery data: Connected Sheets. |

## Domain 3: Data pipeline orchestration

| What I picked or thought | What is right | The rule I use now |
|---|---|---|
| I mixed up Dataform and Dataflow. | Dataform runs SQL transformations inside BigQuery, with dependencies and assertions. Dataflow moves and transforms data on its way in, batch or streaming. | Data already in BigQuery and the work is SQL: Dataform. Data in motion: Dataflow. |
| A scheduled job that keeps polling a bucket for new files. | A Cloud Run function (used to be Cloud Functions) triggered by the file-created event. | One step started by an event: an event-triggered Cloud Run function. No polling. |
| Managed Service for Apache Airflow (used to be Cloud Composer) for a few serverless API steps in a row. | Workflows. The Airflow service is for heavy work: many dependent pipelines, backfills, Python operators. | A few service calls in order: Workflows. Many dependent pipelines: Airflow. |
| The Airflow service for "run this at a recurring interval". | Cloud Scheduler. It is a clock (cron). Airflow can run on a schedule but is built for multi-step pipelines. | A recurring interval and one thing to call: Cloud Scheduler. |
| Eventarc as the central orchestrator across systems. | The Airflow service. Eventarc routes one event from A to B and does not care what happens next. An orchestrator runs step 1, waits, runs step 2, retries, and tracks state. | Eventarc is the router. Cloud Run functions are the doer. Cloud Scheduler is the clock. Airflow is the conductor. |
| I treated the orchestrator and Dataflow as two options for the same job. | Airflow decides when and in what order tasks run, as a DAG (a directed acyclic graph of tasks). Dataflow is one processing engine, and it can be one step inside that DAG. | The orchestrator decides when. The engine does the work. |
| Two separate tools for batch and streaming. I also expected Pub/Sub to do some processing. | Apache Beam is the code and Dataflow is the engine that runs it. The same pipeline code handles batch and streaming. Pub/Sub only delivers messages. It never computes. | Beam is the code, Dataflow is the engine, Pub/Sub is delivery. |
| I mixed up a dead-letter topic and a monitoring alert. | A dead-letter topic only parks messages that could not be delivered. Being told about a problem is an alert in Cloud Monitoring. | Dead-letter topic keeps the failed messages. An alert tells a person. |

## Domain 4: Data management

| What I picked or thought | What is right | The rule I use now |
|---|---|---|
| Object versioning to recover a BigQuery table. | Versioning is a Cloud Storage feature. BigQuery has time travel (up to 7 days back), table snapshots, and table clones. | BigQuery undo is time travel, then snapshots. Versioning is for buckets. |
| I mixed up a table snapshot and a table clone. | A snapshot is a read-only copy of a table at a point in time. A clone is a copy you can write to. | Keep a frozen copy: snapshot. Need to change the copy: clone. |
| One role would be enough to run a query. | You need two: BigQuery Job User on the project where the query runs, and BigQuery Data Viewer on the dataset that holds the data. The job runs and bills in the project it starts from, even when it reads data in another project. | Job User where I run. Data Viewer where the data lives. |
| A broad role, or a grant on the whole project, to give someone access to one dataset. | Grant the smallest role on the smallest resource. Data Viewer on the dataset is enough to read. | Least privilege: the dataset, not the project. Viewer, not Owner. |
| I guessed on uniform vs fine-grained bucket access. | Uniform bucket-level access means IAM only. Fine-grained means IAM plus an access control list (ACL) on each object. | One rule for the whole bucket: uniform. Exceptions per file: fine-grained. |
| An authorized view to hide one sensitive column. | A policy tag on the column. It is defined once in a taxonomy, is reusable across tables, and needs no extra views. Hiding rows is a different feature: row-level access policies. | Hide a column with no extra views: policy tag. |
| I mixed up the encryption options, and picked customer-managed keys when nothing required them. | Default encryption is always on and needs no setup. CMEK (customer-managed encryption keys): the keys live in Cloud KMS and you control them. CSEK (customer-supplied encryption keys): you supply the keys yourself, and BigQuery does not support it. | No key requirement: default. "We must control the keys": CMEK with Cloud KMS. |
| I mixed up Knowledge Catalog (used to be Dataplex) and BigQuery sharing (used to be Analytics Hub). | Knowledge Catalog is for finding and understanding your own data: search, quality, lineage. BigQuery sharing is for giving data to others. | Understand my data: Knowledge Catalog. Hand data to others: BigQuery sharing. |
| I guessed on how to make a bucket survive a region outage with at most 15 minutes of data loss. | A dual-region bucket with turbo replication. Default replication can take up to 12 hours. | Region outage and a 15-minute recovery point: dual-region plus turbo replication. |
| Cloud SQL high availability (HA) to survive a region outage. | HA covers a zone failure, with automatic failover. A region outage needs a cross-region replica that you promote. | Zone failure: HA. Region failure: cross-region replica. |
| Partition expiration to delete whole old tables. | Partition expiration only drops old partitions and the table stays. To remove whole tables after a set time, use the dataset's default table expiration, which applies to new tables. | Trim old days: partition expiration. Remove tables: table expiration. |
| Clustering or materialized views to lower the storage bill. | Those lower query cost, not storage cost. Storage cost drops with partition expiration and with long-term storage pricing, which applies automatically after 90 days without changes. Reading the data does not reset the 90 days. | Query cost: partition and cluster. Storage cost: expire data and let long-term pricing apply. |
| Custom code to move or delete old files in a bucket. | Lifecycle rules on the bucket do it with no code: move objects to a colder storage class at one age and delete them at another. | Age-based moves and deletes in a bucket: lifecycle rules. |
